# 負荷と通信量を減らす改善案

2026-11-04 の検討メモ。
実装方針の決定や効果の保証ではなく、計測して優先順位を付けるための候補を残す。
現状の記述は、この日のコード確認に基づく。

## 前提

チャンクの重複排除、zstd 圧縮、HTTP の長期キャッシュ、並列先読み、翻訳済みコードの保存はすでにある。
次は取得するデータ量と実行する処理量を減らす方向を調べる。
通信量だけでなく、ゲームが読み込みで止まる時間も一緒に評価する。

## 1. 先読みの予算と使用率

`web/src/play.ts` の `readAhead` は、前回読んだチャンク一覧を4並列で取得する。
ゲーム自身の通信を優先する制御はあるが、一覧全体を処理するため、今回は使わないデータも先読みする可能性がある。
`crates/kura/src/vfs.rs` の記録上限は8,192チャンクで、256 KiB のチャンクなら最大約2 GiB相当になる（非圧縮の概算であり、実際の転送量ではない）。

- タイトル到達までの起動用データと、その後のデータを分ける。
- 転送量とメモリ使用量に先読み予算を設ける。
- 先読みしたデータのうち、実際に読まれた割合を記録する。
- シークや場面変更を検知できる場合は、古い先読み予約を破棄する。
- 読み込み停止時間が増えない範囲で、使用率の低い先読みを減らす。

変更候補: `web/src/play.ts`、`crates/kura/src/vfs.rs`、履歴の保存処理。

## 2. メモリキャッシュの追い出し方

チャンクキャッシュは既定128 MiBで、挿入順に追い出す。
キャッシュヒット時に順序を更新しないため、繰り返し使うデータも連続読み込みに押し出される。

- LRU、または一度だけ読むデータと再利用するデータを分ける方式を比較する。
- 未使用の先読みデータは低い優先度にする。
- 音声などの連続読み込みがキャッシュ全体を占有しないようにする。
- 追い出した後の再取得回数と、再展開に使う CPU 時間を測る。

HTTP キャッシュで再通信を避けられても、展開やコピーの負担は残り得る。
ネットワークキャッシュとメモリキャッシュの効果を分けて測る。

変更候補: `crates/kura/src/vfs.rs`。

## 3. JIT キャッシュの段階読み込み

`web/src/play.ts` の `loadJit` は、一覧の全パーツを `Promise.all` で取得してコンパイルする。
保存コードが増えると、起動時の取得量とコンパイル負荷が増える可能性がある。

- 起動時に必要なコード、頻繁に使うコード、特定の場面だけのコードを実行履歴から分ける。
- 起動用を優先し、残りは必要に応じて読み込む。
- 未取得のコードは既存のインタプリタや JIT で実行できる構成を検討する。
- ダウンロードとコンパイルの同時実行数に上限を設け、ピーク負荷を比較する。

細分化しすぎるとリクエスト数やモジュール管理の負担が増える。
追加ロード時のコード登録と実行中スレッドの整合性も設計が必要。

変更候補: `web/src/play.ts`、`host/vnjit.js`、`crates/kura/src/jit.rs`、`crates/ippai/src/serve.rs`。

## 4. 静止画面での CPU と GPU 負荷

入力待ちの30秒間について、ゲームのポーリング、タイマー、x86 実行、描画命令、テクスチャ転送、画面合成の負荷を分けて測る。

- 待機 API が適切にスレッドを休止させているか確認する。
- 変更のないリソースの再転送や画面合成を減らす。
- GDI の dirty rect 処理はすでにあるので、D3D 側も含めて余分な処理を探す。

一律の低 FPS 化は文字送りや演出の時間を変える可能性がある。
ゲームの時間進行、入力、音声を維持したまま改善する。

調査候補: `crates/sake` の待機処理、`crates/kura/src/display.rs`、描画バックエンド。

## 5. アクセス特性に合わせたチャンクサイズ

小さいランダム読み込みでは、小さめのチャンクで過剰取得を減らせる可能性がある。
連続読み込みでは、大きめのチャンクでリクエスト数を減らせる可能性がある。

- まず既存のサイズ指定で64 / 128 / 256 / 512 KiBを比較する。
- 圧縮率、実際に読んだ量に対する転送量、リクエスト数、停止時間を測る。
- 効果があれば、ファイル単位やアーカイブ内部でサイズを変える方式を検討する。

可変サイズ化にはストア形式と VFS の変更が必要。
ゲームがアーカイブをどう読むかによって効果が変わるため、拡張子だけで判断しない。

変更候補: `crates/ippai/src/pack.rs`、`crates/kura/src/vfs.rs`。

## 6. 不変の JIT パーツを事前圧縮

JIT 配信は動的圧縮を使っている。
不変パーツの生成時に圧縮版も作れば、配信ごとのサーバー CPU を減らせる可能性がある。

- 保存完了後に圧縮版を生成し、完成したファイルを公開する。
- 既存のキャッシュとバージョン管理を保つ。
- 同時利用時の CPU と応答時間、追加の保存容量を比較する。

変更候補: `crates/ippai/src/serve.rs`。

## 7. 重いライブラリ処理の置き換え

画像展開、音声デコード、メモリコピーなどが x86 実行時間の大部分を占める場合、直接コンパイルした Wasm やブラウザの機能へ置き換える案がある。
まずは既知の DLL の明確な関数境界を候補にする。

関数の識別、呼び出し規約、戻り値、副作用を合わせる必要があり、互換性の検証コストは高い。
計測で支配的な処理を特定してから取り組む。

画像や音声の再圧縮も別の候補だが、ゲームが期待するファイル形式をどう提供するかが課題になる。
エンジンや形式ごとの対応が必要なので、汎用の改善より後に検討する。

## 計測と着手順

`web/src/meter.ts` には転送量、HTTP キャッシュ利用、読み込み停止時間などの計測がある。
未使用の先読み量、メモリキャッシュから追い出した後の再取得量、JIT の取得量とコンパイル時間を追加する。

初回起動、再起動、セーブからの再開、静止画面を同じ操作で比較する。
HTTP キャッシュと JIT キャッシュの有無、端末、回線条件を記録する。
端末の CPU、メモリ、GPU と、サーバー CPU を分けて評価する。

| 順番 | 候補 | 狙い | 規模の目安 |
| --- | --- | --- | --- |
| 1 | 先読みの使用率と過剰取得量の計測 | 無駄の特定 | 小 |
| 2 | 先読み予算とキャッシュ改善 | 通信量と再展開の削減 | 小〜中 |
| 3 | 不変 JIT パーツの事前圧縮 | サーバー CPU 削減 | 小〜中 |
| 4 | 静止画面の待機と描画改善 | 端末負荷の削減 | 調査次第 |
| 5 | JIT の段階読み込み | 起動負荷と通信量の削減 | 中〜大 |
| 6 | チャンク構成の最適化、重い処理の置き換え | 追加の改善 | 大 |

順番は暫定。
計測結果に合わせて入れ替える。
