# プレイ記録と暗号化 S3 ストレージ

## プレイ記録

サーバーのストア直下に `library.sqlite3` を作る。
ゲーム情報画面からお気に入りとメモを保存でき、一覧の「統計」からゲーム別の累計プレイ時間を確認できる。
時間はゲーム起動後、タブが表示されている間を15秒ごとに記録する。
読み込み中とバックグラウンドの時間は対象外とし、プロセス強制終了直前の未送信時間は失われる場合がある。
同じセッションの再送は二重加算しない。

セーブの正本はサーバーに置く。
S3 未設定時は SQLite に保存し、設定時は S3 に暗号化して保存する。
ブラウザの OPFS は補助キャッシュとして残し、サーバーにセーブがない場合だけ旧セーブを移す。
他端末で更新されたセーブへの上書きは HTTP 412 で拒否する。
ネットワーク障害を「セーブなし」として起動しない。

## .ippai パッケージ

ゲーム情報画面の「.ippai を書き出す」でダウンロードし、同じ画面から復元する。
復元は現在のセーブ、メモ、お気に入りを置き換える。
プレイ履歴はセッション ID で統合する。

形式は ZIP で、`manifest.json` と任意の `saves.bin`、`web.bin` を含む。
マニフェストには形式バージョン、起動設定、ゲーム内容の照合情報、個人記録を格納する。
ゲーム本体、JIT キャッシュ、S3 の鍵や認証情報は含めない。
パッケージ自体は暗号化していない。

v1 は同じチャンク構成のゲームへの復元に対応する。
元のゲームフォルダの物理パスと登録名は異なってよい。
元の仮想パスと起動設定を復元し、マウント先だけを復元先の tree 名へ置き換える。
ファイル内容、パス、サイズを照合し、ホスト側の更新日時とパーミッションは照合しない。
別のゲームや破損したパッケージは拒否する。

## S3 の設定

旧 `VNVM_S3_*` 設定は使わない。
`IPPAI_STORAGE_CONFIG` に次の TOML ファイルのパスを指定する。
このファイルはストアと Web 配信ディレクトリの外に置き、読み取り権限を管理者に限定する。

```toml
bucket = "ippai"
region = "us-east-1"
# S3 互換サービスを使う場合だけ指定
# endpoint = "https://s3.example.com"
prefix = "ippai/"
active_key = "key-2026-11"

[keys]
key-2026-11 = "<ランダムな32バイト鍵を64文字の16進数で指定>"
```

認証は AWS の通常の認証情報チェーンを使う。
共通鍵はパスワードではなく、暗号学的乱数から生成した256ビット鍵を使う。
設定ファイルと共通鍵は S3 と別の場所へバックアップする。

```sh
export IPPAI_STORAGE_CONFIG=/secure/ippai-storage.toml
ippai add /path/to/game --id sample --exe game.exe
ippai storage push
ippai storage backup
ippai serve
```

`push` は登録済みストアを順番にアップロードする。
チャンクは登録時に圧縮済みで、配信時には再圧縮しない。
内容ハッシュが既存のチャンクは再アップロードしない。
ゲーム一覧と tree の変更は再アップロードする。
アップロード後もローカルの元ファイルは自動削除しない。

S3 オブジェクト名は UUID v4 で、ゲーム名と元ファイル名を含まない。
各オブジェクトを個別のデータ鍵で AES-256-GCM 暗号化し、その鍵を共通鍵で暗号化する。
対応表と暗号化済みデータ鍵は SQLite に保存する。
サーバーが取得時に認証と復号を行う方式で、E2EE ではない。
認証が完了するまではデータをクライアントへ返さない。
S3 取得はストレージインスタンスごとに最大8並列とし、1 MiB以下の取得結果を合計64 MiBまでメモリに保持する。

## DB バックアップと復元

```sh
ippai storage backup
# 表示された UUID を復元用に保存する
ippai storage restore <UUID> /new-store/library.sqlite3
ippai --store /new-store serve
```

復元先の親ディレクトリを作成してから実行する。
既存 DB への上書きは拒否する。
バックアップは SQLite の Online Backup API で作成し、zstd 圧縮後に暗号化する。
WAL 適用前の DB 本体を単純にコピーする方式は使わない。

復元に必要な暗号化済みデータ鍵は、UUID で取得できる小さなバックアップ情報として DB の外に保存する。
バックアップ当時のオブジェクト鍵を復元する情報も、別のデータ鍵で暗号化して同梱する。
復元時にその情報を使い、DB 内のオブジェクト鍵を現在の共通鍵で包み直す。
DB の認証と `integrity_check` が成功してから、新規ファイルとして公開する。
復元後の起動時にゲーム一覧と tree を取り戻し、ゲームのチャンクは S3 から取得する。

バックアップの定期実行は、上記 CLI を systemd timer などから実行する。
自動削除は実装していないため、古いバックアップが参照する S3 オブジェクトも保持される。
S3 ライフサイクルによる一律削除は、保持中バックアップからの復元を壊す可能性がある。

## 共通鍵の変更

同一 DB に書き込むサーバーを停止したうえで、設定へ新しい鍵を追加し、`active_key` を変更する。
旧鍵も残して以下を実行する。

```sh
ippai storage rotate
ippai storage rotate-backup <保持するバックアップのUUID>
```

保持する各バックアップに `rotate-backup` を実行する。
更新するのは鍵の包みだけで、ゲーム、セーブ、DB スナップショットの暗号文本体は変更しない。
全バックアップの変更と復元確認を終えてから旧鍵を設定から外す。
バックアップ情報の古い S3 バージョンを保持する場合は、そのバージョンに必要な旧鍵も別途保持する。

## fetch の順序保証

Wasm の同期ファイル API は保ち、ページ側で作成した通信 Worker が fetch を実行する。
ゲーム Worker ごとに MessagePort を渡し、要求ごとの共有バッファで結果を対応付ける。
通信 Worker はデータ受け取り確認を非同期に待つため、別の要求を止めない。
初期化時にページ側で必要な tree は、Wasm の factory 呼び出し前に取得する。

Web ゲームの Node 互換 `readFileSync` はページスレッド上で実行されるため、対象ディレクトリのファイルを起動前に4並列で取得する。
この種類のゲームは全量取得の時間とメモリが必要になる。
Windows ゲーム側は従来どおり必要なチャンクを取得する。

## 検証コマンド

```sh
cargo test -p ippai --bin ippai
node tests/fetch-bridge.test.mjs
cd web
vp test
vp check
vp build
```

Rust のストレージ統合テストはローカルの S3 模擬 HTTP サーバーを使う。
暗号化、改変拒否、鍵変更前後で暗号文本体が不変であること、旧鍵なしの復元、パッケージ往復を検証する。
加えて、GHA の `rustfs` ジョブでは固定ダイジェストの RustFS コンテナを起動し、実際の S3 API でゲームとセーブの暗号化保存、UUID v4 オブジェクト名、チャンク再利用、鍵変更時の暗号文本体の不変性、旧鍵なしの DB 復元、カタログ復元、リモートチャンク取得、改ざん拒否を検証する。
通常の `cargo test` ではこの外部サービス必須テストは ignored となり、専用ジョブが明示的に実行する。
Docker が使える環境では同じテストを次のコマンドで実行できる。
コンテナは一時ポートとテスト専用認証情報を使い、終了時に削除する。

```sh
bash tools/ci/test-rustfs.sh
```

本番 S3 の IAM ポリシーや運用上の性能は別途接続先で確認する。
