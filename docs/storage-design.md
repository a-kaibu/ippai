# ゲーム管理と暗号化ストレージの設計

2026-11-05。実装の設計メモ。操作手順と制約は [storage.md](storage.md) を参照。

## 要件

- SQLite にお気に入り、メモ、プレイ履歴を保存し、統計画面を提供する。
- ゲーム本体を含まない `.masu` パッケージにセーブ、設定、個人情報、履歴、ゲーム識別情報を格納する。
  同じゲーム本体と組み合わせてプレイ状態を復元する。
- XHR を fetch に移行する前に、起動順序、並列要求、失敗、保存の順序をテストする。
- S3 は旧バックアップ実装の拡張ではなく、新しいストレージ層として設計する。
- ゲーム本体とセーブを S3 に暗号化して保存し、必要な単位を取得する。
- 共通鍵を変えてもデータ本体の再暗号化を必要としない。
- オブジェクト名にゲーム名や元ファイル名を含めず UUID v4 を使う。
- SQLite 自体も整合したスナップショットを暗号化して S3 にバックアップする。

## 保存単位と鍵

ゲームの登録時にチャンク化と圧縮を行い、その後に認証付き暗号で暗号化する。
各不変オブジェクトにはランダムなデータ鍵を割り当て、データ鍵を共通鍵で暗号化する。
暗号文には形式バージョンとオブジェクト UUID を結び付け、別オブジェクトへの差し替えを検出する。
S3 への書き込み完了を確認してから、SQLite に公開する参照を確定する。
途中で失敗したアップロードは参照されないオブジェクトとして後から回収できるようにする。

サーバーが復号を担う。E2EE ではない。
共通鍵は S3 と DB の外に置く。
ローテーションでは新旧鍵を識別し、データ鍵の包みだけを更新する。
既存バックアップの包みを含めて更新が完了するまで旧鍵を廃棄しない。
暗号文本体は変更しない。

## SQLite バックアップ

WAL を使っている DB の本体ファイルだけをコピーする方式は採らない。
SQLite のバックアップ機能で整合したスナップショットを作り、圧縮後に専用のデータ鍵で暗号化する。
バックアップの暗号化済みデータ鍵、鍵 ID、形式バージョンなどの復号情報は、DB の外にある小さな包みとして S3 に保存する。
DB がなくても、S3 と外部管理の共通鍵から復元できることを必須条件にする。

バックアップ本体と包みは UUID v4 で識別する。
本体のアップロード完了後に包みを公開し、不完全なバックアップが復元候補にならないようにする。
復元時は一時ファイルで認証と SQLite の整合性を検証してから入れ替える。
稼働中の DB を直接上書きしない。
バックアップが参照するゲームとセーブのオブジェクトは、そのバックアップの保持期間中は削除しない。

## 通信の順序

Wasm の同期ファイル API と、JavaScript の非同期通信を分ける。
ネットワーク処理を担当する実行環境は、待機中のゲームスレッドに依存してはならない。
要求ごとに応答の対応を管理し、失敗時も待機を必ず解除する。
マウント情報とセーブのロードが完了してからゲームを起動する。
セーブの送信は順序制御と競合検出を行い、失敗した保存を完了済みと扱わない。

## 代替案と懸念

S3 側のサーバー管理暗号化だけでは、要求されているアプリ側の共通鍵管理と鍵の再包装を満たさないため採用しない。
ゲーム全体を一つの暗号文にすると、小さな読み込みで過大な取得と復号が必要になるため、独立したチャンクにする。
チャンクを極端に小さくすると S3 リクエスト数と管理データが増えるので、既存のサイズを出発点として測定する。

Web ゲームの Node 互換 `readFileSync` はメインスレッドで呼ばれる。
fetch を同期的に待つことはできないため、起動前の事前取得が必要になる。
この種類のゲームは同期 API の互換性を保つため、起動前の全量取得を採用する。

## 検証

- DB の移行、再起動後の保持、統計の重複送信と日付境界。
- `.masu` の往復、異なるゲームへの復元拒否、破損と不正パスの拒否。
- fetch の逆順応答、並列要求、通信失敗、起動前のロード完了。
- セーブの送信失敗、再試行、複数端末からの競合。
- 暗号文の改変拒否、誤った鍵での失敗、鍵変更前後で本体が不変であること。
- 空の環境へ S3 と共通鍵だけから DB バックアップを復元すること。
- アップロード中断とバックアップ保持期間中のオブジェクト保護。

実環境での接続テストに使う S3 の指定は未確認。
専用のローカル検証環境で実装を進め、実バケットの確認とは区別する。
